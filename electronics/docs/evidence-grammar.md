# Monogate Course Evidence Packet Grammar

Status: active course contract
Schema: `monogate-electronics.course-evidence-packet.v0`

Every Monogate Electronics course should end with a claim-bounded evidence
packet. The goal is not only to make the circuit work. The goal is to teach the
engineering habit:

```text
claim -> simulate -> build -> capture -> compare -> constrain
```

The reusable course design rules live in
[`docs/course-design-standard.md`](course-design-standard.md). In short: use
Forge when the course claim benefits from a checkable boundary, not as decoration.

## Packet Shape

Each course packet should include these sections:

- course claim;
- simulation evidence;
- physical evidence;
- sim-vs-hardware comparison;
- domain safety lens;
- blocked claims;
- artifacts and links;
- review status.

The reusable folder convention is:

```text
evidence/courses/<course_id>/<packet_id>/
```

For Reflex Lab 01:

```text
evidence/courses/reflex_lab_01/reflex_lab_01_reflexcourse_YYYY_MM_DD/
```

The older Trainer Board folder remains valid as a compatibility evidence lane:

```text
evidence/reflexcourse/
```

## Required JSON Fields

The canonical machine-readable packet file is:

```text
evidence_packet.json
```

It must contain:

```json
{
  "schema_version": "monogate-electronics.course-evidence-packet.v0",
  "packet_id": "reflex_lab_01_reflexcourse_YYYY_MM_DD",
  "course_id": "reflex_lab_01",
  "course_title": "Reflex Lab 01: Pot to Guarded Output",
  "kernel_id": "threshold_reflex_v0",
  "board_id": "reflexcourse-C906D4",
  "board_revision": "reflexcourse_breadboard",
  "esp32_chip_mac": "B4:BF:E9:C9:06:D4",
  "evidence_level": "draft",
  "review_status": "draft",
  "claim_flags": {
    "simulated": false,
    "hardware_observed": false,
    "live_serial_capture_performed": false,
    "certified_safety_claim": false,
    "production_controller_claim": false
  },
  "sections": {},
  "artifacts": {},
  "blocked_claims": []
}
```

`certified_safety_claim` and `production_controller_claim` must remain `false`
for course packets.

## Claim Flags

Use these flags in every public or deploy-facing packet:

```json
{
  "simulated": true,
  "hardware_observed": false,
  "live_serial_capture_performed": false,
  "certified_safety_claim": false,
  "production_controller_claim": false
}
```

For a real bench packet, `hardware_observed` and
`live_serial_capture_performed` may become `true` only after operator-approved
live capture. A dashboard export alone is still a draft until physical
artifacts such as photos, video, or measurements are attached.

## Artifacts

A strong packet should include:

- firmware-reported board identity when available;
- JSONL trace;
- validation output;
- replay output;
- dashboard graph PNG or screenshot;
- dashboard session log or summary;
- wiring photo before power;
- demo photo or video link;
- optional measurements or waveform notes;
- `PACKET_MANIFEST.json` generated by `tools/make_packet.py`.

## Tools

Create a reusable course packet starter:

```powershell
python tools\scaffold_course_evidence.py --course-id reflex_lab_01
```

Validate a reusable course packet:

```powershell
python tools\validate_course_evidence_packet.py evidence\courses\reflex_lab_01\reflex_lab_01_reflexcourse_YYYY_MM_DD
```

Generate a SHA-256 manifest after artifacts are present:

```powershell
python tools\make_packet.py evidence\courses\reflex_lab_01\reflex_lab_01_reflexcourse_YYYY_MM_DD --out evidence\courses\reflex_lab_01\reflex_lab_01_reflexcourse_YYYY_MM_DD\PACKET_MANIFEST.json
```

## Review Boundary

Course packets are evidence for education and review. They are not certified
safety artifacts, agency acceptance, or production-controller readiness. Public
copy should stay inside the claims supported by the packet.
